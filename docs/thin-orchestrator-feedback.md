# Thin Orchestrator 写作反馈与升级决定

以下是当时的采纳记录。图像格式与状态字段后来根据 Graphify 实际流程调整，当前执行规则以 [任务与状态契约](../references/task-and-state.md)、[产物契约](../references/article-artifacts.md) 为准。

这份记录来自一次文章任务后的人工调整与其他 Agent 反馈。它用于约束本次 Skill 升级，并保留暂不固化的建议；单次案例不自动变成所有文章的硬规则。

| 建议 | 决定 | 理由与实施边界 |
| --- | --- | --- |
| 1. `article_mode` 五种体裁 | 采用 | 模式影响提问、产物、大纲和审稿；保留现有文件名以兼容旧项目。 |
| 2. 中立请求使用 `analysis` | 采用 | 明确的“陈述和分析，不做观点倾向”高于历史风格；标题和正文不默认套观点句式。 |
| 3. 三类判断分离 | 采用 | `source-claim`、`analysis-hypothesis`、`author-position` 分别记录来源、推论和作者确认状态。大纲候选不自动成为作者观点。 |
| 4. “思路 ok，内容不 ok”触发重写 | 采用 | 继承已认可的方向，归档旧稿，从正文结构与材料选择重新写，不仅润色措辞。 |
| 5. 每张图片都有 SVG 和 PNG | 限定采用 | 本 Skill 新制作的**图示**交付两种格式，正文默认引用 PNG、SVG 留作源文件。截图、照片、外部授权图片不适用此格式要求。 |
| 6. 图片嵌入与渲染 | 分层采用 | 脚本检查所支持的 Markdown/HTML 图片引用、相对路径和文件存在；Agent 在目标渲染器实际预览并记录结果。文件检查不能代替视觉渲染。 |
| 7. `diagram-spec.md` | 采用 | 仅在制作图示时建立，逐图记录章节、解释目标、证据 ID、SVG/PNG 目标和验证结果。 |
| 8. 四种状态分离 | 采用 | `project.md` 分别记录正文、视觉、渲染、审稿状态，避免有 `article.md` 就称完成。 |
| 9. 修复 `check-article.js` | 采用 | 针对 `figure`/`figcaption` 误报、相对路径和 HTML 图片增加行为测试，再修脚本。 |
| 10. 中文技术文章“AI 味”检查 | 定性采用 | 四个维度进入编辑审查，并指出具体句段；不引入未经校准的“观点密度”“抽象名词密度”分数或固定案例比例。分析稿本来就不应被强迫增加观点。 |
| 11. “文章完成”门槛 | 采用 | 只有正文、必要图示、嵌入、实际渲染和审稿均过关才称完整文章完成。阶段任务仍可只交付阶段产物。 |

## 本次实施

1. 调整 `SKILL.md` 和写作参考，使模式选择、判断归属、重写与完成门槛一致。
2. 补充图示规格和四种状态的产物契约；更新中英文 README 中会影响使用者预期的说明。
3. 先用失败测试复现图片检查误判及漏检，再修改 `check-article.js`，运行全部测试与 Skill 校验。

## 验收场景

- 给出“陈述和分析，不做观点倾向”且没有作者立场：`article_mode=analysis`，写分析问题与证据边界，标题和正文不借用观点文模板。
- 给出大纲候选判断而没有作者确认：证据表记为 `analysis-hypothesis`；用户说“思路 ok”仅保留方向，不把候选改为 `author-position`。
- 用户说“思路 ok，但文章内容不 ok”：旧 `draft.md`/`article.md` 存档，正文重写，渲染与审稿状态重新检查。
- 新生成一张图：先有逐图规格，交付 SVG/PNG，正文引用 PNG；脚本检查引用和基本文件结构，目标渲染器实际预览并记录后才可称完成。

## 继续积累

- 数值化“AI 味”阈值：先收集多种体裁的人工标注样本，确认指标和误报成本后再考虑自动化。当前只记具体问题和修改依据。
- 一键保证图片在所有渠道可渲染：需要明确目标发布渠道与渲染器；目前以目标渠道实际预览为准，保存验证记录。
- 全部图片一律双格式：若未来渠道只接受特定格式，或图片是照片、截图，再按实际交付需求制定转换策略；不将本次图示要求泛化。
