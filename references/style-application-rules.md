# Style Application Rules

用于把初稿改成用户偏好的技术文章风格。先读本次 `article_mode`；以下观点写作建议只在 `opinion` 或用户明确要求表达判断时采用。

## 总体风格

- 开头尽早交代文章要解决的问题；`opinion` 可先给已确认的判断，再解释原因。
- 技术细节服务当前模式的解释、操作、评价或判断。
- 语气克制，不写宣传稿。
- 默认像资深工程师给同事讲系统：可以自然口语，不俚语化，不堆情绪词、感叹词和口头禅。
- 只有材料支持时才从工具或案例上升到更一般的方法；不要强行提炼趋势。
- 读者应能看出作者如何使用证据，而不是只看到资料堆叠。
- 风格重写先做减法：删解释腔、总结腔、多余转折和套话；原句自然、准确、清楚时不改。
- 面向非工程师读者时，减少居高临下的称呼、训人语气和过深术语，优先写“我怎么用、读者怎么试”。

## 开头

`opinion` 的开头可以包含：

- 一个反常识信号。
- 一个明确判断。
- 一个更大的问题框架。

`analysis` 的开头可以直接说明研究对象、为什么需要分析、本文覆盖哪些机制与边界；标题描述对象或问题，不默认用“真正的”“关键不是”等观点型措辞。

避免：

- “随着 AI 的快速发展……”
- “本文将详细介绍……”
- 大段背景铺垫后才出现观点。

## 论证

每一节至少承担一种功能：

- 定义对象：它是什么，不是什么。
- 拆解机制：它为什么能工作。
- 对比差异：它和常规做法的区别。
- 趋势判断：它说明什么变化。
- 边界条件：它不适合什么场景。
- 方法论上升：对产品、Agent、workflow 的启发。

## 段落

- 段落短，单段只承载一个意思。
- 必要时用显式转折：但、真正的问题是、从工程视角看。不要为了过渡反复写“这说明”。
- 关键判断可以单独成段。
- 避免长串形容词和抽象名词堆叠。

## 避免模板化表达

不要把“真正值得关注的不是 X，而是 Y”“从工程视角看”“这说明”等句式当作段落模板。只有证据和具体差异确实支持时才使用对比；`analysis` 不用这些句式制造观点倾向。

## `opinion` 中的个人判断

表达已确认判断时给出边界：

- “我更倾向于把它理解成……”
- “对高合规团队，这是优势；对只想快速写代码的团队，它可能显得重。”
- “这个验证不足以证明生成质量，但足以说明产品形态。”

## 图表与表格

需要图表的情况：

- 有流程链路：用 flowchart。
- 有层次结构：用 layered diagram。
- 有阶段演进：用 timeline / evolution chart。
- 有方案比较：用 table。
- 有系统架构：用 architecture diagram。

不要为了好看而画图。每张图都要回答一个论证问题。

草稿阶段可用 Mermaid、文字图或表格表达。新制作的正式图示先写 `artifacts/diagram-spec.md`，再在 `assets/` 保存可编辑源文件和目标渲染器支持的成稿格式；正文使用相对路径。若目标渠道需要 PNG，导出并检查像素尺寸和文字可读性。实际在目标 Markdown 渲染器打开成稿检查图片和图说，结果记入 `review/render-check.md`。截图、照片或外部图片按原始格式、来源许可与渠道要求处理。

## 中文技术文章的人工审稿信号

审稿时指出具体句段和修改理由，不给文章套未经校准的“AI 味”总分：

- **观点密度**：`opinion` 的关键判断是否有证据与边界；`analysis` 是否被强塞立场句。
- **模板化过渡**：段首是否反复使用“首先、其次、综上”“这说明”“真正的问题是”等空转连接。
- **抽象名词密度**：连续使用“能力、体系、范式、生态”等词时，是否缺少机制、对象或操作细节。
- **具体案例比例**：关键解释是否有合适的例子、数据或反例支撑；不规定固定比例，避免给无案例可用的题材编造案例。

## 禁止或慎用

- 不要把工具写成无条件推荐。
- 不要把官网文案当成自己的判断。
- 不要堆“颠覆、革命、赋能、生态闭环”等泛化词。
- 不要只列功能清单，要解释功能背后的结构。
- 不要在没有来源时写确定性事实。
- 少用“说白了”“其实”“你会发现”“谁能想到”推进段落。
- 不要用“综上所述”“一句话总结”“可以看出”这类标签替代自然收束。
