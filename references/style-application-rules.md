# Style Application Rules

用于把初稿改成用户偏好的技术文章风格。

## 总体风格

- 先给判断，再解释原因。
- 技术细节服务产品判断和趋势判断。
- 语气克制，不写宣传稿。
- 默认像资深工程师给同事讲系统：可以自然口语，不俚语化，不堆情绪词、感叹词和口头禅。
- 文章要从工具进入方法论，从案例进入结构性变化。
- 读者应该感觉作者在做技术判断，而不是整理资料。
- 风格重写先做减法：删解释腔、总结腔、多余转折和套话；原句自然、准确、清楚时不改。
- 面向非工程师读者时，减少居高临下的称呼、训人语气和过深术语，优先写“我怎么用、读者怎么试”。

## 开头

好的开头通常包含：

- 一个反常识信号。
- 一个明确判断。
- 一个更大的问题框架。

避免：

- “随着 AI 的快速发展……”
- “本文将详细介绍……”
- 大段背景铺垫后才出现观点。

## 论证

每一节至少承担一种功能：

- 定义对象：它是什么，不是什么。
- 拆解机制：它为什么能工作。
- 对比差异：它和常规做法的区别。
- 趋势判断：它说明什么变化。
- 边界条件：它不适合什么场景。
- 方法论上升：对产品、Agent、workflow 的启发。

## 段落

- 段落短，单段只承载一个意思。
- 必要时用显式转折：但、真正的问题是、从工程视角看。不要为了过渡反复写“这说明”。
- 关键判断可以单独成段。
- 避免长串形容词和抽象名词堆叠。

## 可用句式

- 真正值得关注的不是 X，而是 Y。
- 从工程视角看，X 的价值不在于 A，而在于 B。
- 这已经不是“做一个文档”，而是把某件事变成可执行协议。
- 它提醒我们，问题不只是模型能力，而是流程结构。
- 如果说 X 解决了内循环，那么 Y 试图处理外循环。

这些句式只在承载真实对比或判断时使用，不要连续套用成模板。

## 技术文章中的个人判断

要写出判断，但要给边界：

- “我更倾向于把它理解成……”
- “对高合规团队，这是优势；对只想快速写代码的团队，它可能显得重。”
- “这个验证不足以证明生成质量，但足以说明产品形态。”

## 图表与表格

需要图表的情况：

- 有流程链路：用 flowchart。
- 有层次结构：用 layered diagram。
- 有阶段演进：用 timeline / evolution chart。
- 有方案比较：用 table。
- 有系统架构：用 architecture diagram。

不要为了好看而画图。每张图都要回答一个论证问题。

正式图表选择目标渠道能正确渲染、且便于后续修改的格式。草稿阶段可用 Mermaid、文字图或表格表达；需要单独交付的图片放在 writing project 的 `assets/`，并在成稿中引用相对路径。

## 禁止或慎用

- 不要把工具写成无条件推荐。
- 不要把官网文案当成自己的判断。
- 不要堆“颠覆、革命、赋能、生态闭环”等泛化词。
- 不要只列功能清单，要解释功能背后的结构。
- 不要在没有来源时写确定性事实。
- 少用“说白了”“其实”“你会发现”“谁能想到”推进段落。
- 不要用“综上所述”“一句话总结”“可以看出”这类标签替代自然收束。
